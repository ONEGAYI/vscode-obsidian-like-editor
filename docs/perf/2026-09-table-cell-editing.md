# 表格单元格编辑性能边界（工单 #12）

状态：2026-09-24，实现工单 #12 时实测。测量环境：jsdom + node（vitest，无真实布局）；阈值回归用例在 `test/unit/liveTable.test.ts`「千行单表性能边界」，本文件记录其数值结论与已知限制。

## 结论

**千行级单表在首版架构下无性能风险**：装饰是纯数据（RangeSet mark/line 类，无 widget DOM），成本只出现在构建与增量维护两条路径上，均远低于交互阈值。

| 单表规模 | 全量装饰构建 | 单格编辑增量更新（中位） |
| --- | --- | --- |
| 100 数据行 | 7.2 ms | < 0.1 ms |
| 1000 数据行 | 11.2 ms | 0.02 ms |
| 3000 数据行 | 25.4 ms | < 0.1 ms |

- **全量构建**只在 create / 全文替换（init/resync）时发生；千行表约 11 ms，一次性成本。
- **增量更新**：单格编辑只重扫变更行与受影响节点（`liveDecorations` 的增量策略），与表格总行数无关；实测亚毫秒。增量结果与全量重建逐项一致（`RangeSet.eq` 对拍，见回归用例）。
- **写回链路正确性**：千行表首/末行单元格编辑经 webview → edit.request → 宿主文档 → 保存回读逐字一致（回归用例固定）。
- **无整表 DOM**：live 侧表格编辑面即 CM6 源文本行（管道符可见、mark 装饰样式化），不存在整表控件实例；CM6 视口外行不创建 DOM（既有红线，`large.md` 集成用例覆盖）。屏外表格行的装饰数据常驻 RangeSet（与标题/列表装饰同一语义），不构成 DOM 成本。

## 单表大小边界

单表是一个 Table 语法节点、装饰按行增量维护，**没有**类似「超大围栏按行细分」（FENCE_CHUNK_LINES）的块内拆分需求：表格每行是独立的 TableRow 节点，编辑只触碰所在行。3000 行单表（约 25 ms 全量构建）仍远低于可感知阈值；理论上限受整篇文档装饰构建成本约束（与 #5/#7 已测的万行级文档结论同向），不设硬性行数上限。

## 已知限制与修复记录

1. **live 跨管道 code span 无内联代码高亮**：`@lezer/markdown` 的 TableCell 切分不识别行内代码内的 `|`（把 `` `x|y` `` 切散），跨 cell 的 InlineCode 节点不存在——本项目单元格定位用自研 GFM 拆分（`tableCells.ts`）不受影响，但 lezer 驱动的 `vsidian-inline-code` 装饰在此形态下不发射（源文照常可见可编辑）。
2. **阅读视图代码内管道渲染已修复（#22）**：解析前以等长字符暂时代替行内代码中的管道符，token 化后还原，表头与数据行不再错切或丢列。单测覆盖普通与双反引号 code span，真实 1.86.2 宿主集成用例核对行内代码节点；源文本保持原样。
3. **粘贴含 `|` 文本不自动转义**：键入钩子只覆盖 `|` 键（keydown 路径）；粘贴内容中的裸管道保持原样写入（保存后渲染按未转义管道切列）。#13 已评估并保持不动（工单范围固定单点粘贴语义，不做区域粘贴处理）；如后续支持须补 paste 钩子。
4. **`\`` 转义反引号不参与 code span 配对扫描**（`tableCells.ts` 简化，罕见形态）：`\`` 后的 `` ` `` 仍按普通反引号参与 run 匹配，极端构造下单元格边界判定与 GitHub 有差异。
5. **live 源码形态不重排列对齐**：GFM `:---:`/`---:` 对齐以稳定类（`vsidian-table-align-*`）落在单元格上，但源文一维布局不改变（对齐的视觉语义由阅读视图的真实 table 呈现）；写回不做重排对齐（所见即所键）。
